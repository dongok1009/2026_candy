# RCI/TRIX 이식 컨텍스트 노트

## 지표 정의 (구현 근거)

**RCI (Rank Correlation Index)** — 스피어만 순위상관 기반 추세 지표.
```
RCI = (1 − 6·Σd² / (p³−p)) × 100      d = 시간순위 − 가격순위
```
- 시간순위: 최신 봉이 1
- 가격순위: 최고가가 1, **동일가는 평균순위(tie-average)** 로 처리
- 범위 −100 ~ +100. +100은 완전 상승 정렬, −100은 완전 하락 정렬

**TRIX** — 삼중 EMA의 1기간 변화율(%).
```
e1 = EMA(close, p) → e2 = EMA(e1, p) → e3 = EMA(e2, p)
TRIX = (e3[i] − e3[i−1]) / e3[i−1] × 100
Signal = EMA(TRIX, signalPeriod)
```

## 결정 사항

### 1. 중첩 EMA의 null 정렬을 `realignTo`로 처리
`calculateEMA`는 워밍업 구간을 null로 채운 배열을 반환한다. 이를 다시 EMA에 넣으려면
null을 걸러내야 하는데, 그러면 결과 배열이 짧아져 인덱스가 어긋난다.
→ `realignTo(src, vals)`로 원본의 non-null 위치에 되돌려 정렬한다.
**기존 MACD 시그널 계산이 쓰는 방식과 동일**하므로 새로운 패턴이 아니다.

### 2. 전략은 새 파일 `Logic.v8.2.7.cjs`로 만든다
프로젝트 규칙: 기존 전략 파일은 수정하지 않고 복사해 새 번호를 붙인다.
서버가 `Logic.v8.2.6.cjs`를 쓰고 있으므로 원본을 건드리면 실전에 즉시 영향이 간다.

### 3. 신규 필터 기본값은 OFF
검증 전에는 매매 동작이 바뀌면 안 된다. OFF 상태에서 v8.2.6과 결과가
**완전히 일치**하는 것을 2단계 통과 조건으로 삼는다. 일치하지 않으면 이식 과정에
의도치 않은 변경이 섞인 것이므로 다음 단계로 넘어가지 않는다.

### 4. TRIX 시그널 기간을 룰별로 가변 지원
백테스트에서 시그널 기간(기본 9)을 바꿔가며 탐색할 수 있어야 한다.
→ 룰에 등장하는 기간들을 모아 `trix_sig_{n}` 배열을 각각 미리 계산해 둔다.
매 봉마다 EMA를 다시 도는 것보다 훨씬 빠르다.

### 5. `bybit_trader.cjs`는 이번 작업에서 제외
실전 봇 파일을 건드리면 재시작·검증 부담이 생긴다. RCI/TRIX는 아직 채택 여부가
결정되지 않았으므로, 백테스트·대시보드에서 검증 가능한 상태까지만 만든다.
채택이 결정되면 그때 봇에 배선한다.

**5단계에서 재확인** — 봇 파일 수정은 애초에 불필요했다. `bybit_trader.cjs:12`가
`require('./strategies/' + strategyVersion)`으로 전략을 동적 로드하고,
`:176`/`:226`에서 `indicators_logic`·`signal_logic`을 그대로 호출한다.
즉 `STRATEGY_VERSION=Logic.v8.2.7`로 지정하면 RCI/TRIX 필터가 실전 주문에 이미 적용된다.
**남은 공백은 브라우저 대시보드뿐이었다.**

### 6. 프론트엔드 구조 차이 대응
구 저장소는 `RulesEditor.jsx` / `TradeLogTable.jsx` / `exportUtils.js` /
`rulesNormalizer.js`로 분해돼 있으나, 신 저장소는 `BacktestForm.jsx`(1,917줄) 하나다.
→ 파일을 복사하지 않고 **해당 monolith 안의 대응 위치에 삽입**한다.
프론트 구조 리팩터링은 이번 작업 범위가 아니다(요청받지 않은 변경 금지).

## 진행 중 기록

### 1단계 완료 (지표 계산)

`lib/indicators.cjs`와 `src/shared/utils/indicatorUtils.js` 양쪽에 `realignTo`·`calculateRCI`·
`calculateTRIX`를 추가했다. 두 사본이 같은 값을 내는지 테스트로 고정했다.

**검증 17건 통과.** 확인한 성질.
- 단조 상승 → RCI +100, 단조 하락 → −100
- p = 9/26/52에서 무작위 500봉 전 구간 −100~+100 유지
- TRIX 시그널선이 trix 배열과 인덱스 정렬되고, 시그널 기간이 길수록 늦게 시작
- **백엔드/프론트엔드 두 사본 출력 완전 일치** (사본 분기 방지)

#### 발견: 전 구간 동일가일 때 RCI = 50
스피어만 간이식 `1 − 6Σd²/(p³−p)`는 **동점이 없을 때만 유효**하다. 전 구간 동점이면
가격순위가 모두 `(1+p)/2`가 되어 `Σd² = 60`, `denom = 720` → 결과 50이 나온다.
수학적으로는 정의되지 않는 구간이며 50은 축약식의 산물이다.

BTC 1분봉에서 9봉 연속 종가가 완전히 같을 일은 없으므로 **특수 처리하지 않았다**
(일어나지 않는 시나리오에 방어 코드를 넣지 않는다는 원칙). 대신 테스트로 동작을 고정해
나중에 값이 바뀌면 감지되도록 했다. 부분 동점은 평균순위로 정상 처리된다.

### 5단계 착수 (라이브 대시보드)

목적이 바뀌었다. 애초 4단계 UI는 "백테스트에서 값을 눈으로 본다"였는데,
사용자 의도는 **백테스트에서 성적이 좋은 조건을 그대로 실전매매 조건으로 채택하고,
그 전에 라이브 화면에서 신호를 검증한다**는 것이다.
→ 차트 패널 표시만으로는 부족하고, **라이브 판정 로직이 백테스트와 일치**해야 한다.

#### 발견: 대시보드 판정 로직은 전략 파일과 별개의 사본이다
`PriceChart.jsx:556`의 `evaluateSignal()`은 `Logic.v8.2.x`의 `signal_logic`을
브라우저용으로 다시 구현한 병렬 사본이다(ADX·MACD·Stoch·RSI만 평가).
따라서 룰에서 RCI/TRIX를 켜도 화면의 LONG/SHORT/HOLDING 표시는 그것을 무시한다.
**백테스트·실전 판정과 화면 표시가 어긋나는 상태**였다.

이상적으로는 판정 로직을 한 곳으로 합쳐야 하지만, 그건 이번 요청 범위 밖의
대규모 리팩터링이다(요청받지 않은 변경 금지). → 기존 구조를 유지한 채
`evaluateSignal`에 RCI/TRIX 분기만 **전략 파일과 동일한 의미로** 추가한다.
Logic.v8.2.7 `:359-380`의 판정식을 그대로 옮긴다.
- 롱: `rci9 > rci26`, `trix > signal`
- 숏: `rci9 < rci26`, `trix < signal`
- 값이 null이면 필터를 통과시킨다(전략 파일과 동일 — 워밍업 구간에서 신호를 죽이지 않음)

#### 결정: 지표 배열을 ref에 캐시해 crosshair 재계산을 피한다
`PriceChart.jsx:286-300`의 crosshair 핸들러는 **마우스가 움직일 때마다**
RSI·MACD·Stoch·ADX를 전 구간(1,000봉) 재계산한다. 이미 무거운데
RCI는 창마다 정렬을 도는 O(n·p·log p)라 9/26 두 개를 여기에 더 넣으면 체감 렉이 생긴다.
→ 데이터 경로에서 계산한 RCI/TRIX 배열을 `rciTrixRef`에 저장하고,
crosshair에서는 인덱스로 읽기만 한다. 기존 재계산 코드는 건드리지 않는다(수술적 변경).

#### 결정: 차트에 그리는 TRIX 시그널선은 롱 룰 기간을 쓴다
시그널 기간은 롱/숏 룰이 각각 다를 수 있으나 라인은 하나만 그릴 수 있다.
→ 차트는 롱 룰 기간(기본 9)으로 그리고 범례에 기간을 표기한다.
판정(`evaluateSignal`)은 롱·숏 각각의 기간으로 따로 계산한 시그널선을 쓴다.
두 기간이 같으면(실사용 대부분) 배열을 재사용한다.
